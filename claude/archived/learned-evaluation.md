# Learned evaluation (per-feature submodules in `eval.rs`)

**Archived:** the five per-feature submodules in `eval.rs` were removed; whole-board networks trained by `rotor-train` replaced them (architectures.md), and the hand-crafted evaluation is PeSTO only (pesto-evaluation.md).

## Status

Five small submodules exist in `eval.rs`, hand-written Rust forward passes, each with a
zero-initialized output layer -- provably no-ops on Rotor's actual play until trained. Training
for any of them is not yet designed or started.

**Gate**: cleared. The original blocking condition (Rotor's search dramatically better than the
old depth-4/no-pruning/material-only baseline) is satisfied -- search now has pruning,
extensions, iterative deepening, and a transposition table.

**Relationship to `rotor-train`'s whole-board network**: this per-feature-submodule architecture
is considered superseded as the long-term plan by `rotor-halfkp.md`/`rotor-halfkav2hm.md`/
`rotor-naive.md`'s single whole-board network -- that design's "replace, not layer on top"
decision means it's meant to eventually retire these submodules rather than train them
individually. No code change has followed from that in `eval.rs` yet; these five submodules
remain the current shipped code, unaffected by `rotor-train`'s own progress (a separate binary,
with no play-time loading into `rotor` built yet regardless).

## Constraint

Training labels always come from Rotor's own search, never another engine's output (CLAUDE.md
rule 1). Hand-written CPU inference for a submodule with a provably-zero output layer carries
none of the "learning from an unproven engine" risk the strength gate above is about, which is
why these five could be built ahead of that gate.

## Implementation pattern common to all five

- **Input**: a raw "subboard" -- board facts scoped to the submodule's own concern, not
  pre-aggregated hand-picked numbers.
- **Architecture**: one hidden ReLU layer, `H` sized by the `H = sqrt(I*O)` heuristic (a
  placeholder, not validated against real training data), 2 linear outputs (mg/eg) fed into the
  existing `taper(mg, eg, phase)`.
- **Initialization**: hidden layer weights/bias small and random (He/Kaiming-scaled,
  `stdev = sqrt(2/fan_in)`), output layer weights/bias exactly zero -- provably zero contribution
  to eval until trained, while staying trainable (an all-zero init would freeze the whole network
  permanently via a ReLU symmetry deadlock: zero output gradient reaches the hidden layer either
  way). Generated by a seeded CPU PRNG living in shared library code, so a future training tool
  would start from the exact same numbers the shipped binary ships with.
- **Implementation split** (CLAUDE.md rule 7): hand-written Rust for inference (built, for all
  five); `tch-rs` for training (deferred, not built for any of them) -- to be cross-checked by an
  explicit forward-pass equivalence test once both exist for a given submodule.

## The five submodules

1. **King danger** -- 1151 binary inputs per color (king-ring attack-exists, opponent material,
   own ring occupants, blockers-for-king). `H ~= 48` (~55K params). **Unwired** from
   `material_value`: cost measured too high pending `search.rs` pruning (wiring it in briefly
   took the test suite from 5.81s to 103.36s).
2. **Pawn shield/storm** -- 102 binary inputs per color (3-file x 8-rank corridor around the
   king, plus a 6-wide center-file one-hot). `H = 14` (1,472 params). **Wired in**, replacing the
   old TSCP-derived `king_safety_penalty` mechanism outright (see `king-safety.md`); old code
   deleted.
3. **Imbalance** -- 90 binary inputs per color (piece-count one-hot, 5 types x 9 buckets x 2
   sides). `H = 13` (1,211 params). **Wired in**, replacing the old quadratic-form `imbalance`
   mechanism outright, including the bishop-pair bonus; old code deleted.
4. **Pawn structure** -- 192 binary inputs per color (whole-board pawn occupancy, 3-category
   one-hot). `H = 20` (3,902 params). **Wired in**, replacing `is_isolated`/`is_doubled_file`/
   `is_backward`'s contribution to `material_value`. Old functions/constants kept as
   `#[allow(dead_code)]`, the one deliberate exception among the five: it's the only replaced
   mechanism that produced real useful signal untuned, so the code stays available rather than
   needing reconstruction once training exists.
5. **Threats** -- 9024 binary inputs per color (two 64x64 attack/defense matrices, one 64x13
   occupant array). `H = 134` (~1.2M params, by far the largest). Built and unit-tested but
   deliberately **never wired** -- cost alone (over a million parameters, dense 4096-element
   multiplies) makes it a non-starter before `search.rs` pruning exists; not even measured.

## Not yet settled

- Training for any of the five submodules -- deferred, not designed how or when.
- Whether other features (PST, etc.) get the same submodule treatment.
- The practical path for the "replace, not layer on top" transition to a whole-board network
  actually reaching `eval.rs`.
