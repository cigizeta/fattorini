# MoE-based learned evaluation architecture

Superseded, see rotor-halfkp.md -- the Router/Expert mixture and the Bypass it fed on top of are
both retired outright, not paused; Rotor HalfKP's own king-conditioned feature transformer covers
what the king-based routing was for, and the bypass concept itself didn't hold up once compared
against real engines with and without it.

## Status

Design settled in full. **Gate** (inherited from `learned-evaluation.md`): actual training
(`tch-rs`/GPU, anything touching labels generated by Rotor's own search) may proceed once the
search generating those labels is dramatically better than the old depth-4, no-pruning,
material-only baseline -- cleared: search now has pruning, extensions, iterative deepening, and a
transposition table. The eval itself is explicitly allowed to be weak at generation 0, since
replacing it is the point; each generation's resulting strength still has to be measured, not
assumed. See `learned-evaluation.md`'s own Status section for the gate's full reasoning. The
near-term priority is validating the MoE architecture itself, not producing a strong engine on the
first pass.

**Narrow exception**: hand-written, torch-free CPU forward-pass code may proceed now if the network
it computes is provably a no-op (zero output) until training happens -- the pattern already used
for the five existing hand-crafted submodules (king danger, pawn shield/storm, imbalance, pawn
structure, threats). The router/experts are eligible for it too.

**Implementation status**: `rotor-train`'s network module (`network.rs`) has `KingEmbedding`,
`Accumulator`, `Router`, and `Expert` built and tested against the real `tch`/`libtorch`
environment. `Bypass`'s own visibility blocker is now resolved: `piece_value_mg`, `piece_value_eg`,
and the seven PST tables moved out of `eval.rs` into their own new, always-`pub` module,
`src/material.rs` -- the same shape as the `rotor::phase` precedent (a small dedicated file, not
scattered `pub` items left in place), settled specifically because duplicating the numbers directly
in `rotor-train` was rejected (a real, if slow-moving, staleness risk once `eval-tuning.md`
actually retunes `piece_value_mg`/`eg`) and widening `eval.rs`'s own surface in place was rejected
too. `eval.rs` now just imports from `material` like any other caller would; nothing about its own

**`Bypass` is now written and tested** (`network.rs`): two `nn::Linear(768, 1)` layers, `mg` and
`eg`, each seeded (under `no_grad`, bias forced to zero) from `material::piece_value_mg`/`eg`

`own_one_hot` (`[batch, 768]`, own perspective only -- `Bypass` never touches the accumulator or

not `eval.rs`'s private `game_phase`/`PHASE_MAX` scale), computing `bypass_mg`/`bypass_eg` as two
plain dot products then fusing them as `bypass_mg * phase + bypass_eg * (1 - phase)`. Five tests

negation, the mg/eg taper specifically at the king (the one piece type where the two PST tables

**`Network` is now written and tested** (`network.rs`): wires `Accumulator`, `Router`, all 8
`Expert`s (`EXPERT_COUNT`), and `Bypass` into one `forward` -- `sum weight_i(king, phase) *
expert_i(accumulator)` (via `Tensor::cat` over the 8 expert outputs times the router's own mixture
weights, summed) plus the tapered bypass term, returning a single `[batch, 1]` scalar. Two tests:
output shape, and the actual architectural invariant `moe.md` calls out -- at initialization, every
expert's zero-initialized output layer makes the mixture term contribute exactly 0, so the whole
network's output is checked to be identical to a standalone `Bypass` fed the same inputs, not just
assumed from each submodule's own separate zero-init test. `cargo test --bin rotor-train --features
training network::tests` passing in full (17/17).

**The sparse-cache-to-dense-tensor path is now written and tested.** `batch.rs`'s `to_dense_batch`
expands a slice of `cache::CacheRecord`s into exactly the tensors `Network::forward` expects
(`own_one_hot`/`opponent_one_hot` `[batch, 768]`, `file_rank_one_hot` `[batch, 16]` in

**AdamW is now hand-rolled and tested** (`adamw.rs`), not `tch`'s built-in `nn::AdamW`: that
built-in optimizer turned out to have no way to serialize its own internal state at all (checked
directly against `torch-sys`'s complete `ato_*` FFI surface, no `state_dict` equivalent anywhere),
which would have meant either a cold-started optimizer at every epoch boundary (real cost,
compounding across potentially hundreds of epochs) or dropping the one-epoch-per-invocation run
shape entirely -- neither of which matches real industry checkpointing practice. Instead, `AdamW`
owns its own `m`/`v` moment buffers as plain tensors, serializable via the same
`Tensor::save_multi`/`load_multi` primitive `VarStore::save`/`load` use internally. Cross-checked
step by step against `tch`'s own built-in `nn::AdamW` (CLAUDE.md rule 7's discipline, applied to a
hand-derived formula), plus a save/load round-trip test proving a restored optimizer reproduces the
exact next update an uninterrupted run would have made. See `training.md`'s own "Weight handoff"
section for the full writeup.

**The epoch loop and `rotor-train train` are now written and tested.** `epoch.rs`'s `run_epoch`
shuffles the train cache's row order (via `CacheFile::shuffled_row_order`), trains one pass through
`Network`/`AdamW` (MSE loss via `tch`'s own built-in `mse_loss`), then runs one no-grad pass over
the test cache -- both passes share one `run_batches` helper, so train and test loss are guaranteed
to come from the exact same forward pass and loss function. Three tests: output shape/finiteness,
a real end-to-end check that training loss actually falls over 20 epochs on a trivial fixed-target
fixture (proving the whole wiring learns, not just runs), and a check that the no-grad test pass
never mutates any parameter. `main.rs`'s new `train` subcommand ties it to real files: opens both
caches, builds or resumes `Network`+`AdamW` from a checkpoint directory (`model.vs` via
`VarStore::save`/`load`, `optimizer.opt` via `AdamW::save`/`load`), runs exactly one epoch per
invocation (`training.md`'s "Run shape"), reports loss, and saves the checkpoint back --
restartable at this same epoch boundary after a crash or `Ctrl+C`, with no optimizer state lost
(the whole reason `adamw.rs` exists). `cargo build`/`cargo test --bin rotor-train --features
training` both clean (55/55 tests, no new warnings).

## Motivation

Every submodule in `learned-evaluation.md` still has a human-drawn boundary. This design removes
that last hand-authored decision too: let training discover the decomposition itself, under the
same one-PC/one-GPU/tens-of-millions-of-positions budget that makes the submodule approach
tractable.

## Grounding facts

- **NNUE structure**: sparse per-perspective input -> linear feature transformer -> accumulator
  (the only part needing incremental updates) -> concatenate perspectives -> clipped ReLU -> small
  dense trunk -> scalar. The trunk is cheap enough to recompute fully every position regardless of
  any gate.
- **HalfKP/HalfKAv2's king bucketing is not MoE**: a raw board fact selects a weight-matrix slice
  feeding a shared trunk -- a context-conditioned embedding, not a learned router choosing among
  independently trained sub-networks.
- **MoE's usual (LLM) justification doesn't apply here**: decoupling parameter count from
  compute-per-example doesn't matter at chess-eval-net scale. What does apply: **data efficiency
  under a fixed, self-generated training budget** -- letting the network partition its own capacity,
  rather than a human naming what each piece is for.
- **A trunk-level gate doesn't break NNUE's incremental-update property**, since gating happens
  after the accumulator, not on it.
- **Data-budget calibration is unresolved but not alarming**: a non-king-relative ~768-input net is
  real and workable (Caissa reports "a decent net" from ~80M positions; Leorik 3.0 -- 768 inputs,
  256-wide hidden layer, no king bucketing, 622M positions -- reached ~3230-3280 CCRL), well above
  `learned-evaluation.md`'s ~10M Texel-anchor figure and well below HalfKAv2-scale billions. No
  GPU-hours estimate exists yet for Rotor's own target scale (flagged unknown, not a placeholder).

## Settled architecture

**Replace, not layer on top.** Retires all five hand-crafted submodules entirely rather than mixing
on top of them; their code stays as tolerated dead code (same precedent as pawn structure
superseding isolated/doubled/backward).

**Input: not HalfKAv2-scale.** A 22528-wide king-conditioned representation is what drives NNUE's
own billion-position requirement -- infeasible here. Direction: a smaller, non-king-conditioned
shared board representation.

**Input shape: 64 x 13 = 832, one-hot per square over 13 states, per perspective.** Not
12 x 64 = 768 (one-hot piece-type/color plane per square, empty implicit). Each square is one-hot
over `{none, one of the perspective's own 6 piece types, one of the opponent's 6 piece types}` --
the same 13-category occupant-array convention already shipped in `learned-evaluation.md`'s threats
submodule, chosen there specifically so a square is never independently "empty from my side" and
"empty from theirs" at once. Reused here for the same reason, and for consistency with the rest of
the codebase's board-encoding convention.

**"None" is definitionally real but fixed at zero.** The 13th category exists for correctness (a
square is exactly one of empty/own-piece/opponent-piece, avoiding the ambiguity two separate
6-way-plus-empty encodings would have), not because "this square is empty" itself needs to be a
learnable signal. Its weight is fixed at zero, never trainable: matches how real NNUE actually
works (empty squares contribute nothing to the accumulator sum, only occupied ones do), preserves
the incremental-update property (only piece moves need to touch the accumulator, not every empty
square), and means the sparse feature cache only ever needs to record occupied squares (at most 32
per perspective), not all 64. Implementation-wise the accumulator's real trainable weight matrix is
therefore 768-wide (64 squares x 12 non-none categories) per perspective, not 832 -- "832" describes
the conceptual category count, not the trainable parameter count.

**Perspectives are oriented by mirroring, not rotating.** Each color's own perspective is expressed
in a common coordinate frame so the same weights serve both: White's own perspective uses absolute
squares unchanged; Black's own perspective mirrors every square vertically (rank flipped, file
unchanged -- `square XOR 56` under LERF numbering). Confirmed directly against real Stockfish
NNUE's own history: an early version used a full 180-degree rotation instead, later recognized as
wrong specifically because rotation also swaps files, which is incorrect for chess given
side-specific castling rights (rotation is fine for shogi, which has no castling and a rotationally
symmetric start position) -- the fix was a rank-only mirror. The same mirroring applies to the
router's king file/rank input below, for the same coordinate-consistency reason.

**Router placement: fixed in the trunk**, operating on the accumulator's output, never conditioning
the accumulator/feature-transformer stage -- preserves NNUE's incremental-update property.

**Router input: curated (king embedding + phase), not the full board.** Every expert still sees the
full board via the shared accumulator; the router sees only what it's deliberately given, which
keeps "king position dominates routing" enforceable, keeps the router small and inspectable, and
avoids redundantly re-deriving what the accumulator already computes.

- **King embedding**: 16 (one-hot file + one-hot rank) -> hidden 12 (ReLU) -> output 8, ~308 params.
  A raw 64-way one-hot has zero cross-square sharing; (file, rank) restores it, so data-rich
  squares' gradient reaches weights data-poor squares also depend on. Widths are `H = sqrt(I*O)`-rule
  placeholders, not derived. **Whose king**: side-to-move's own king only, one embedding, not two
  (unlike the five original hand-crafted submodules, which evaluate twice per position, once per
  color) -- consistent with the whole network being side-to-move-relative, and matching the
  router's own stated input size of 9 below, which two king embeddings would have contradicted
  (two 8-dim outputs, not one). In the same oriented (mirrored-if-Black) coordinate frame as the
  accumulator inputs above, for the same consistency reason.
- **Phase input**: `phase::phase(board)`, no embedding needed -- already continuous. Reuses
  `rotor-curate`'s own simpler, unclamped phase definition (not `eval.rs`'s private
  `game_phase()`), promoted into a shared `rotor::phase` library module rather than duplicated,
  since two binaries need the identical definition.
- **Router**: king embedding (8) + phase (1) = 9 -> hidden 8 (ReLU) -> 8 expert logits -> softmax.
  Needs its own hidden layer so king and phase actually interact rather than merely add. King and
  phase enter as a plain concatenation, co-equal -- no structural scaling or biased initialization
  favoring one over the other; the router's own weights learn whatever relative dominance the data
  supports.
- **Rejected: one expert per king square (hard partition, no router)** -- structurally HalfKP's own
  king-bucket indexing relabeled. Real king occupancy is heavily skewed toward castled/starting
  squares, so 64 disjoint datasets would likely underperform one shared network. Replaced by the
  learned router above.
- **8 experts, dense (all active, softmax-weighted)** -- not top-1/top-k. 64 (inherited from the
  rejected hard partition) has no remaining justification once routing is learned. 8 balances the
  ~70-100M-position budget across experts against classical eval's own handful of distinct
  positional regimes (opposite-bishop endgames, same/opposite-side castling attacks, pure K+P
  endgames, ...). Dense over top-k/top-1: their real justification (compute savings at large N, or
  per Switch Transformer's own top-1 case) doesn't apply at N=8 with cheap per-expert FFNs, and
  dense avoids fragmenting an already-scarce training budget. Count and activation are starting
  hypotheses to validate once there's data to test alternatives against.

**Accumulator width: 128 per perspective, plain ReLU, not clipped.** The shared per-perspective
feature transformer maps the 768-dim trainable occupant input (see "'None' is definitionally real
but fixed at zero" above) to a 128-wide representation; both perspectives concatenate to 256 before
feeding the router's experts. Chosen deliberately smaller than Leorik 3.0's real precedent (768
inputs, 256-wide, ~3230-3280 CCRL): that result used 622M training positions, roughly 9x this
project's own estimated ~70M (`training.md`'s AB(lambda) design labels every ply of all ~863,790
games rather than sampling a handful per game -- see `training.md`'s own dataset-size estimate),
and a width matched directly to Leorik's on a much smaller fraction of its data still risks
overfitting, flagged as a real capacity risk at this scale (not underfitting) -- treated as a
starting hypothesis to validate against measured train/test loss (CLAUDE.md rule 5), not a derived
number. The real capacity gap is smaller still once whole-network parameter counts are compared
directly rather than just accumulator width: this design's actual total (~133,000 params across
accumulator, king embedding, router, all 8 experts, and the bypass -- see "Each expert" below) is
smaller than Leorik's own plain NNUE (~197,000), not larger, despite the extra experts, since this
accumulator is half Leorik's width. **Plain ReLU, not clipped ReLU**, despite the clipped-ReLU
precedent in real NNUE: that clipping exists specifically to bound activations for int8
quantization at inference time, a concern that doesn't apply yet, since training runs in float32
and quantization is a separate, later concern for the hand-written CPU forward pass.
**Concatenation order: side-to-move-first, not White-first.** Confirmed directly against real
Stockfish (`nnue_feature_transformer.h`, and the NNUE docs): the 512-wide concatenated vector
(here, 256-wide) always places the side-to-move's own 128-wide accumulator first and the
opponent's second, flipping which physical accumulator that means depending on whose turn it
actually is. Matches `search.rs`'s existing negamax convention (every score already relative to
whoever is about to move) and real NNUE practice (the same weights serve both colors, since the
network only ever needs "me" and "opponent," never "White" and "Black" as separate concepts).
Rejected: White-first/absolute ordering, which would mismatch both precedents and require an extra
sign-flip step wherever the network's output feeds into negamax search.

- **Each expert: 256 (concatenated accumulator) -> hidden 16 (ReLU) -> 1 (scalar), not a single
  linear layer.** A purely linear expert would be structurally redundant with the linear
  material/PST bypass already in the design (a sum of linear functions is still linear), unable to
  represent anything the bypass doesn't already cover, undermining the actual motivation for having
  8 separate experts (distinct nonlinear positional regimes) in the first place. Hidden width 16
  from the same `H = sqrt(I*O)` placeholder rule already used for the router and king embedding
  (`I = 256`, `O = 1`): roughly 4,100 params per expert, ~33,000 total across all 8, modest relative
  to the accumulator's own ~98,000 feature-transformer parameters (`768 x 128 + 128` bias -- one
  shared weight matrix scored twice per position, once per perspective, not two independent
  matrices, since both perspectives reuse the identical weights). Whole-network total across every
  component (accumulator, king embedding, router, all 8 experts, bypass): ~133,000 parameters --
  smaller than Leorik 3.0's own plain NNUE (~197,000, from its shared `768 x 256` feature
  transformer plus a `512 x 1` output layer, the same real precedent already cited above), despite
  having 8 separate experts, because this design's accumulator is half as wide (128 vs. Leorik's
  256 per perspective) and each expert is kept deliberately small.

**Each expert's output layer (hidden 16 -> 1) is zero-initialized, weight and bias both.**
Everything upstream of it (hidden layer, accumulator, router) keeps `tch`'s default random init --
only the final layer is forced to zero, so every expert outputs exactly 0 at the start of training
regardless of its input. This makes the whole network's initial output just the seeded bypass (real
PST values), matching the "provably a no-op until trained" pattern already used for the hand-crafted
submodules above, rather than the bypass's real signal summed with 8 lots of random noise.

**No load-balancing loss.** The Shazeer-et-al./Switch-Transformer auxiliary loss is standard for
sparse top-k MoE, where it fixes two problems specific to hard routing: compute imbalance across
experts (each on a capacity-limited device) and gradient-starvation collapse (only chosen experts
get any gradient at all). Neither is a standard-fixture problem under dense routing here: there is
no dispatch decision to balance compute over, and every expert gets some gradient every step,
proportional to its softmax weight, regardless of the router's preference.

**Linear material/PST bypass, included.** A direct linear path from the shared 768-dim occupant
input (see the "'None' is definitionally real but fixed at zero" section above for why 768, not
832) to the output, running alongside the expert mixture rather than through it. Seeded at today's
real `piece_value`/PST numbers, not zero -- material/PST already have a citable source, unlike
expert weights. Matches real precedent: Stockfish NNUE's own feature transformer output feeds both
a small linear PSQT readout and the deep nonlinear stack, summed. The reason it's needed rather
than left for the experts to reconstruct: a ReLU hidden layer can only represent an already-linear
function like material by spending two hidden units per input dimension (`relu(x) - relu(-x) = x`),
which wastes capacity better spent on genuinely nonlinear positional reasoning.

**`taper` applies only to the bypass.** The router's own phase input already makes the *expert
mixture* phase-aware, since the softmax weights themselves vary continuously with phase, letting
the combined output `sum weight_i(king, phase) * expert_i(accumulator)` blend across up to 8
experts as phase changes -- a strictly richer mechanism than a two-point `taper`, so applying
`taper` to the mixture too would be redundant, doubling every expert's output width for no real
expressive gain. The bypass is the one exception: it never touches the router or the accumulator, a
direct linear map straight from the raw 768-dim input, so it has no access to phase in any form
otherwise, and real material/PST values are genuinely phase-dependent (a king's activity is good in
the endgame, risky in the middlegame, exactly what `eval.rs`'s own separate mg/eg PST tables
already encode). So the bypass is, concretely, a PST with separate `mg`/`eg` weight vectors
(`bypass_mg = sum input[j] * mg_weight[j]`, `bypass_eg = sum input[j] * eg_weight[j]`, each seeded
from the matching mg/eg table entry divided by the RMS divisor, own pieces positive and the
opponent's negative per the side-to-move-relative convention), fused by
`taper(bypass_mg, bypass_eg, phase)` into a single value, then summed with the (untapered) expert
mixture's own output. Each expert stays a single scalar (`256 -> 16 -> 1`, as already settled
above), not an `(mg, eg)` pair.

**Implementation split: governed by CLAUDE.md rule 7, no exception.** No torch on the CPU, ever. One
hand-written, bitboard-based Rust forward pass for actual play; one `tch-rs` implementation for
training on the GPU. The two are proven equivalent via unit tests (exact golden-value comparisons)
and statistical tests (agreement across a broad position distribution), never assumed to agree. This
applies to the router/experts exactly as it already applies to the five existing submodules.

## Win probability reporting (UCI), a separate concern from the eval network

Real Stockfish reports a win/draw/loss percentage alongside its raw `score cp` in UCI `info` output,
computed by a `win_rate_model`: a curve fit relating (eval score, material remaining) to an actual
win probability, since the same centipawn edge means a different practical winning chance in a
materially rich middlegame than in a stripped-down endgame. This is unrelated to the MoE eval
network's own architecture above -- it consumes an already-final eval score, after `taper`, and
never touches search.

**Settled: a small calibration network, separate from the MoE eval network and from `training.md`'s
own AB(lambda) methodology.**
- **Inputs**: the final eval score (the tapered bypass plus the untapered expert mixture, summed) and
  material remaining on the board -- both inputs, matching Stockfish's own two-input model, not
  material alone. Score says how big the edge is; material says how much game is left for that edge
  to matter.
- **Output**: a win probability.
- **Use: UCI reporting only.** Computed once per reported PV, after search has already finished
  producing its final score -- never inside the search tree, never affecting a pruning or move-
  ordering decision. This is a real, deliberate scope boundary: unlike the MoE eval network itself,
  this calibration network carries none of alpha-beta's soundness risk (a slightly-off displayed
  percentage is a cosmetic defect, not a search-correctness bug), and isn't gated by the club-level
  playing-strength gate the way training that touches actual evaluation is -- it never influences
  what Rotor plays, only what it reports having played.
- **Training data**: the same master-game PGN database `training.md` already settled on (moves and
  results only) -- actual game outcomes give a real, non-fabricated win/draw/loss label to correlate
  against (eval score, material) pairs computed by Rotor's own search over those games' positions.
  `centipawn-calibration.md` implements a distinct, simpler, closed-form (non-learned) version of
  the same underlying question, against today's raw hand-crafted `evaluate()` rather than this
  network's eventual output.
- **Implementation split**: still governed by CLAUDE.md rule 7, same as the main eval network --
  hand-written Rust forward pass for the shipped engine's own UCI output, `tch-rs` for training,
  checked for equivalence. Lower-stakes than the main eval network's own soundness requirement, but
  the same verification discipline applies by default (CLAUDE.md rule 4) absent a reason to relax it.

## Open questions

None currently open. The one prior open question -- whether this architecture needs anything from
`training.md`'s own labeling methodology beyond being its target -- is resolved: `training.md`'s
AB(lambda) design changed only how each position's regression label is computed, never what the
network consumes (still one bounded scalar per position), so no architecture change followed from
it.
