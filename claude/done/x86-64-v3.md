# x86-64-v3: one build, named by its level, and a refusal instead of a crash

Status: implemented 2026-10-25, steps 1 to 4 (DEV.md named no flag, so step 5 had nothing to do).
`bin/rotor bench` 3,117,647 nodes before and after the switch, the same tree. The refusal is
accepted untested (the developer, 2026-10-25). `cargo test --release -p rotor` passing. Done.

## Decisions (the developer, 2026-10-25)

1. **One build, no support for older CPUs.** Rotor needs BMI2, AVX2 and FMA, as today; a CPU
   without them is not supported, and no fallback build is made. AMD Zen 1 and Zen 2 run it with
   their slow, microcoded PEXT, as README already says.
2. **The requirement named by its standard level, x86-64-v3,** and the build compiled for it.
   x86-64-v3 is the three features plus LZCNT, MOVBE, F16C and a few others that every CPU with
   BMI2, AVX2 and FMA also has (Haswell on, every Zen), so the change excludes no machine the
   current flags allow. No A/B measurement: the search is the same program, so its tree is the same,
   and a standard level is preferred over a hand-picked set of flags whatever the speed does.
3. **A clear refusal instead of a crash.** Today nothing checks the CPU: `Bitboard::pext` and
   `pdep` call the intrinsics directly, and the compiler may use AVX2 anywhere, so on an older CPU
   `rotor.exe` dies with an illegal instruction at its first move generation, which a GUI or a
   tester reports as a crash. Instead `main` checks first and exits with one line naming what is
   needed.

## Steps

1. **`.cargo/config.toml`:** `rustflags = ["-C", "target-cpu=x86-64-v3"]` in place of
   `["-C", "target-feature=+bmi2,+avx2,+fma"]`, with a comment saying why the level and not the
   flags (decision 2). Every crate of the workspace builds with it, as today.
2. **`crates/rotor/src/main.rs`:** before the arguments are read, a function checking
   `is_x86_feature_detected!` for `"bmi2"`, `"avx2"` and `"fma"`. If one is missing: to stderr,
   `rotor needs an x86-64-v3 CPU (BMI2, AVX2, FMA): Intel Haswell or later, AMD Zen or later; this
   one lacks <the missing ones>`, then `std::process::exit(1)`. Its doc comment says why it comes
   first, and the caveat below.
3. **Comments citing the old flags:** `board/bitboard.rs` (`pdep`'s safety obligation, which `pext`
   shares) and `simd.rs`'s module comment name the level and the check in `main`, and drop their
   "no runtime check" and the reference to "CLAUDE.md's locked architecture", which CLAUDE.md no
   longer holds.
4. **README, "Running Rotor":** "A CPU with x86-64-v3 (BMI2, AVX2, FMA): Intel Haswell (2013) or
   later, AMD Zen 3 or later. AMD Zen 1 and Zen 2 run it, but slowly. There is no build for older
   CPUs; on one, Rotor says so and exits."
5. **DEV.md**, if it names the flags anywhere: the same level.

## Checks

- `cargo test` passes for every crate.
- `bin/rotor bench` prints the same node count before and after step 1 (the same search tree); its
  nps is noted, not judged.
- The refusal itself: run once on a CPU without BMI2 or AVX2, or under an emulator (Intel SDE with
  an older CPU model), if one is at hand; otherwise accepted untested, its logic being three feature
  queries.

## Caveat

The whole binary is compiled for x86-64-v3, so in principle the compiler may emit an AVX2 or BMI2
instruction before the check runs. `main`'s first lines are a CPUID query and a print, which is how
engines built this way usually refuse, and the risk is small; the emulator check above would settle
it.
